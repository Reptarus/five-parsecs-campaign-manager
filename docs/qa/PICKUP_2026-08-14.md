## 4. The T9-50 lesson — read before editing WorldPhaseController

It took **three** fixes. The first two passed every desk gate and failed on hardware.

`initialize_job_offers()` has **three** callers:

```
1. _fetch_campaign_data() -> _initialize_components_with_data()
2. _show_current_step()   -> _refresh_job_offers()          (:1177, JOB_OFFERS step only)
3. initialize_world_phase() -> _initialize_components_with_data()   (:961)  <- THE CAUSE
```

Number 3 is the orchestrator entry point, and it runs **after** `_ready()` because
`CampaignTurnController` **shows** `WorldPhaseController` each turn rather than
re-instantiating it (its own comment at :900-902 says so). It re-runs
`_initialize_components_with_data()` unconditionally, which clears `job_accepted` AND
re-inits MissionPrep with `world_phase_data.get("mission", {})` — a key that does not
exist, because the mission lives in `job_offer_component.get_accepted_job()`. Its
`if not has_checkpoint()` guard then skips `_show_current_step()`, so nothing re-renders.

> **Rules that came out of this:**
> - A fix ordered against SOME callers is not a fix. `grep` and COUNT before choosing where
>   to insert, or make the fix order-independent.
> - When a screen is REUSED between turns rather than re-created, `_ready()` is not the
>   whole initialisation story. Find the orchestrator entry point and read it first.
> - To disprove a diagnosis cheaply: pick a state where the suspected cause CANNOT fire. At
>   MISSION_PREP `_refresh_job_offers()` is unreachable; the symptom persisted, which killed
>   a wrong answer that had already passed every desk gate.

⚠ Test-fixture trap: `has_checkpoint()` **erases** `_checkpoint_data` as a side effect when
`turn_number` differs from `_current_campaign_turn()`. A hardcoded fixture turn silently
emptied the checkpoint and the test failed WITH the fix in. Derive the turn at runtime.

⚠ Off-by-one when reading a checkpoint against a screenshot: the checkpoint stamps
`turns_played` (a COMPLETED count) while the UI shows `turns_played + 1`.

## 6. Device wrangling (Lenovo TB361FU) — costs an hour if you do not know it

- **`KEYCODE_WAKEUP` does NOT turn the panel on. `KEYCODE_POWER` does.** Swipes sent to a
  dark screen silently do nothing, so unlock attempts fail for no visible reason. Check
  `dumpsys display | grep mScreenState` first.
- Launching the app against an off screen fails hard: `Failed to create vulkan window /
  Unable to create DisplayServer`. The process runs with no rendering surface and the screen
  stays black — easy to misread as a corrupt save.
- `wm dismiss-keyguard` and `cmd statusbar collapse` both failed. What worked: a long swipe
  (`1280,1450 -> 1280,250` over 400ms) with the panel confirmed ON.
- `adb logcat` returns nothing for this app on this device. `user://logs/godot.log` via
  `run-as` is the only usable log; it captures engine errors and ROTATES on launch.
- Set `settings put system screen_off_timeout 1800000` before a long walk; restore to
  `120000` after.

### UI navigation facts that cost three wasted runs

- **"Ready for Battle" is not the battle launcher.** It COMPLETES the Mission Prep step —
  which is why it greys out and the step strip fills to `✓✓✓✓✓✓`. A separate green
  **"Proceed to Battle"** button then appears at the BOTTOM of the page, below the fold.
- **A pixel-diff showing "nothing changed" means the screen has SETTLED.** That is a reason
  to scroll and look elsewhere, not evidence of a hang.
- **CPU means nothing without a baseline.** This app idles at **32% on the main menu, 37% on
  the dashboard**, CPU-time climbing steadily, because Godot renders continuously. ~55% is
  unremarkable.
- The World Phase Back button MOVES when "Next Step" appears. Re-locate it between taps
  rather than chaining blind taps.
